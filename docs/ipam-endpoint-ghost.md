# 容器卡在 `Created`：`Address already in use` 的成因与处置

> 适用：爱快（iKuai）4.x 内置 Docker，容器使用**固定 IP**（挂在自定义网络如 `doc_docker` 上）。
> 关键词：`服务重新启动异常`、`failed to set up container networking: Address already in use`、
> 容器一直 `Created`、重启路由器后必犯。

## 一句话结论

**不是这个 IP 被真实设备占了，是 Docker 网络的 IPAM 里留了一条孤儿 endpoint 记录。**
它没有任何容器引用，删容器、`docker_server down → up` 都清不掉，只有**重建这张网络**能解决。

## 它是怎么产生的

爱快的 `docker_container.update` 不是原地改配置，而是**先删掉容器、再按提交的参数新建一个**
（所以容器 id 每次都会变）。问题出在新建那一步失败时：

1. 旧容器**已经删掉了**；
2. 删除路径直接 `rm` 容器，**没有走 `network disconnect`**；
3. 于是「`IP → 端点`」那条分配记录留在网络的 IPAM 里，而它指向的容器已经不存在了 —— 成了孤儿；
4. 工具（或人）随后把容器建回来，**同一个 IP 又能分配成功**（Docker 分配时会跳过没有容器引用的旧记录），
   表面一切正常、服务也通。

   > v1.6.1 起，工具发现「容器在改镜像时消失」会**自动按更新前的快照 `add` 回来**（退避重试 3 次）。
   > 这救的是**服务可用性**，**不解决幽灵**：容器回来了、IP 还是那个，那条孤儿分配也还在原地。
   > 所以别因为「任务报成功、服务也恢复了」就以为没事。

5. 直到**路由器重启**：Docker 从 `local-kv.db` 恢复网络端点，把孤儿和容器自己那份一起写回 IPAM，
   两条同 IP 记录并存 → 该容器一启动就撞车。

这解释了为什么这个故障的两个特征总是成对出现：**平时跑得好好的，只有重启后才起不来**。

## 证据

一次真实事故的时间线（`history.json` 里 idocker 自己的记录，可直接复核）：

| 时间 | 动作 | 结果 |
|---|---|---|
| 11-15 11:00 | 更新容器，走「搬运」，卡在等下载 600 秒 | 失败，**容器没动**，无副作用 |
| 11-15 11:11 | 再搬一次 | 日志原文：`⚠ <容器> 在改镜像时消失了（爱快删掉后没建回来）→ 正在用更新前的快照重建` |
| 11-17 23:11 | 更新成功 | 容器 `created` 时间 = 日志时间 + 2 分钟，两者吻合 |
| 11-20 重启后 | 容器起不来 | `Address already in use`，全盘只有它一个卡 `Created` |

第 2 行就是幽灵产生的那一刻：**爱快的 update 把容器删了，却没建回来。**

## 为什么只有少数容器中招

同一台路由器上，另一个固定 IP 的容器在这个周期里被更新过 6 次（单 tag 切换、每次一次 update），
从未出事；只有走「搬运」的那个反复出问题 —— 因为搬运在**一个任务里对同一容器连做两次 update**
（先切到版本号 tag，删掉旧记录，再切回 `latest`），「删了建不回来」的机会也翻倍。

> 也就是说：**普通的单次更新不背这个锅，「update 成功删除但新建失败」这条失败路径才背。**
> 而搬运把这条路径的暴露次数放大了一倍。

## 三步判定（全部只读）

1. **看状态**：目标容器是否卡在 `Created`，其余容器是否都 `Up`。
2. **看占用**：LAN 终端表里有没有设备真的用着这个 IP。通常**没有** —— 这就排除了「被别的设备占」。
3. **换 IP 试验**：拿一个一次性的临时容器，分别用「这个 IP」和「另一个空闲 IP」新建。
   - 空闲 IP 能起、这个 IP 报同样的错 → **确认是 IPAM 孤儿，与容器自身配置无关**。

第 3 步是关键，它一次就排掉了「容器参数坏了」「镜像有问题」这些方向。

## 处置：重建这张网络

**先别做「只删这个容器再建」**（轻量方案）—— 实测无效：换个新容器 id 用同一 IP，依旧
`Address already in use`。占用在网络层，不在容器记录上。别在轻量方案上浪费时间。

有效步骤（顺序不能乱，因为 Docker 不允许删除还挂着容器的网络）：

| # | 动作 | 注意 |
|---|---|---|
| 1 | 抓每个容器的 `docker_container show {"TYPE":"inspect"}`，存快照 | `inspect.file_size` 可能是 `"10m"` 这类带单位的字符串，回填前要归一化 |
| 2 | 逐个 `docker_container del` 删掉容器记录 | 镜像、挂载目录、数据卷**都不动**，只是容器 id 会全变 |
| 3 | `docker_network del {id}` 删旧网络 | 若被拒（还有容器挂着）→ 停手，把容器加回去 |
| 4 | `docker_network add` **同名同网段**重建 | `subnet` / `gateway` / `subnet6` / `gateway6` 必须与原来完全一致 |
| 5 | 逐个 `docker_container add` 回填 | 参数取自第 1 步的快照 |

回填时的两个坑：

- **`record.cmd` 是「用户覆盖值」**（为空表示用镜像默认命令），`inspect.cmd` 是最终 argv。
  回填要提交 `record` 的那份，不是 `inspect` 的。
- **`update` / `add` 之后容器 id 会变**。拿流程开始时那份快照里的旧 id 再下发操作，
  爱快会回 `{"code":0,"message":"Success"}` 却什么都不做（和 `docker_image.del` 一个脾气）。
  每一步操作前都要**重读容器拿当前 id**。

代价说清楚：整个过程几分钟内所有容器短暂不可用（反代、DDNS、穿透会断一下），
容器 id 全部变化；**名称、IP、IPv6、镜像、挂载、环境变量、启动命令全部保留**。
网络重建完成后，原来指向「容器 IP:端口」的上游配置（例如宿主机 Docker 守护进程的拉镜像代理）
继续有效，不需要改。

重建后做个自检：`docker_network` 返回的 `containers` 成员数，应当**等于**实际容器数。
刚重建完必然相等；日后若发现成员比实际容器多，说明又产生了新的孤儿。

## 预防

1. **别让容器长期跟随 `latest`，钉在版本号 tag 上。**
   `latest` 每次更新都要走搬运（两次 update），是这条失败路径的高发场景；
   版本号 tag 每次只是单次 update，暴露面小得多。
2. **把「容器在改镜像时消失」当成红灯，不是普通警告。**
   一旦日志里出现这句 —— **即使工具已经自动重建、任务报成功** —— 就说明这次更新留下了孤儿端点。
   服务此刻是好的，但下次重启该容器就会起不来。记一笔，重启后第一时间确认它是否 `Up`。
3. **更新流程里不要并发操作镜像记录。**
   搬运中途手动删镜像记录 / 清任务队列，会让容器在「已删」和「未建」之间被卡住，
   直接踩进这条失败路径。长任务不要用会超时的前台命令行跑（超时被杀 ≠ 任务停止）。

## 边界：为什么不能从根上清掉

爱快的 API 里**没有**「清理某个 IP 的分配记录」这种接口，`docker_server down → up`
也只是重启 Docker 服务、不重建 IPAM。所以唯一的清理手段就是重建网络本身。
要真正根治，只能在**产生端**减少「删除成功、新建失败」的发生（见上一节），
以及在失败发生时立刻重建网络（而不是等到下次重启才发现）。
